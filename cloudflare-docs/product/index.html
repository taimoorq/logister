What your team can do in Logister.

Logister gives your team a shared UI for monitoring apps, reviewing grouped errors, assigning owners, checking recent activity, and understanding whether a project looks healthy. Use this guide to map the screens in Logister to the decisions you make during setup, triage, investigation, and cleanup.

Positioning

Use Logister when production problems need a visible workflow.

The product is organized around the work a team does after an app starts sending signals: scan the dashboard, open the project, choose an issue, assign or close it, and use the detail tabs to understand what happened. The same project screen also holds setup, notifications, team access, and cleanup controls so the day-to-day workflow stays close to the monitored app.

When you are trying to...Use Logister to...
Turn repeated errors into owned workOpen a grouped error, assign an owner, choose a status, and keep occurrence history attached to the issue.
Understand whether one app or all apps need attentionUse the Dashboard for cross-app signals, then open the project for its Overview, Issues, and Explore views.
Explain a failure to a teammateUse the event detail tabs for request context, stacktrace, occurrences, and related logs instead of copying fragments out of separate tools.

Connect services

Start each monitored app as a project.

A project is the workspace for one app or service. It keeps API keys, events, settings, notifications, team access, and retention choices scoped to that app.

Creating a project is a short guided flow: choose the platform that will send telemetry, name the project, and set its data retention. Logister then opens the project's setup path at its first step, where you create the API key (a mobile token for Android and iOS) and send the first event. If you would rather fill in one page, choose Use the quick form on the first step.

Project path

Move from setup to review without leaving the app context.

  • ConnectCreate the project, then follow its setup path through the API key and the first event.
  • ReviewOpen the project card when recent activity or open errors need a closer look.
  • RetireArchive quiet apps when you want history without keeping them in active lists.
You want to...Use the UI to...
Connect a new appCreate a project. The setup path that follows walks through the API key and the first event, then offers the next recommended steps.
Find the next app to reviewScan open errors, latest event, events over seven days, or quiet-project status. Projects that have never received data show Setup needed.
Keep access scopedManage keys and teammates inside that project instead of sharing one global setup across every app.
Retire an app without losing contextArchive the project so it leaves active views but remains available when you need history.

Guided setup

See what is left to set up, and finish it one step at a time.

Settings > Setup lists everything a project can use, grouped by what it unlocks. Steps complete themselves when Logister sees the evidence, such as a first event, a recorded deployment, or a teammate with access; nothing is ticked off by hand. Each step names who does it: you or a project manager in Logister, your code or CI, or the Logister admin when it depends on an instance setting.

GroupServer and web projectsWhat finishing it means
Start receiving data (required)API key, First eventThe project is live. Android and iOS projects use a mobile token, the first diagnostic, and release and build details instead.
Make issues actionable (recommended)Source repository, Deployments, Performance instrumentationStack frames open your code, issues can be compared with releases, and performance views have data. Mobile projects add R8 mapping or dSYM coverage and SDK signals such as sessions.
Bring in your team (recommended)Invite teammates, Your alertsSomeone besides you can triage, and alerts can reach you.
Extend coverage (optional)Link related projects, Check-in monitors, Archive exportsConnected evidence, scheduled-job monitoring, and archived history.

Choose Open path to work through a group one step per screen. Steps done in Logister show the same form Settings uses. Steps done in your code show the integration guide next to a live check that notices the evidence on its own; Check again checks immediately. Save and exit returns to Setup, and progress is never lost because it is read from evidence.

  • The project header shows the setup state on every page, for example Live with the number of recommended steps left. Select it to open Setup.
  • The dashboard lists projects that are still waiting for their first data under Finish setting up.
  • Recommended and optional steps you do not need can be marked Not needed, and undone later. Required steps cannot be skipped.
  • A step that depends on an instance setting, such as outbound email or the GitHub App, shows as blocked and names the Logister admin. Admins get a direct link to the setting.

Project navigation

Every project has the same sections.

The tabs under the project name are the same for every project type, so a Ruby service, an Android app, and a Cloudflare Pages site are all read the same way. What changes is the evidence inside each section. A section that has more than one view shows them just below the tabs.

SectionWhat it holds
OverviewThe telemetry timeline, open error groups, and request timing for the project. Mobile projects show app stability instead.
IssuesGrouped errors, with search, status and assignee filters, and the selected issue's detail.
PerformanceTransactions, request timing, and database load. Mobile projects show app health.
ReleasesDeployments and release health. Android and iOS projects also have Releases (observed builds) and Artifacts (R8 mappings and dSYMs).
ExploreEvents (the activity feed), Charts (live charts built from any signal), Archive (search older telemetry and archive runs), and Connected once the project is linked to another project.
MonitorsCheck-in monitors. The tab appears once the project has a monitor.
SettingsSetup, General, Notifications, Team, Integrations, Connections, Data, and Danger. Application admins also see Admin.
  • Explore keeps your time window, environment, and release when you move between Events, Charts, and Connected.
  • The ? button next to the project name lists walkthroughs for the current section, page tips, and the integration docs.
  • Picking another project from the Projects menu keeps the section you are in, so you can compare Issues across apps without clicking back to each overview.

Dashboard overview

Use the dashboard for cross-app signal before opening a project.

The dashboard has two jobs. Overview is for today's cross-app work: the big chart shows overall activity, My assignments shows work owned by you, and Needs attention highlights open issues that should not be buried in project cards. Projects is for scanning app health one project at a time. Projects that have not received data yet appear at the top under Finish setting up, with a link to continue their setup.

  • Use Explorer when you want to know whether the whole account is getting noisier, quieter, or changing shape by event type.
  • Use My assignments when you already own errors and need to get back to them quickly.
  • Use Needs attention when you want a short list of open problems sorted by recent activity.
  • Switch to Projects when you want to compare apps rather than investigate one chart.

Dashboard rhythm

Start broad, then open the smallest useful view.

  • AccountUse Explorer to spot volume and shape changes across every app.
  • OwnershipUse My assignments when the next action already belongs to you.
  • QueueUse Needs attention when the team has not claimed the newest open work.

Charts

Use Explore › Charts to build a live view from Issues, Events, and Performance signals.

Explore › Charts, also called the Insights workspace, is the project screen for answering, "what is happening here right now?" Use the lens buttons at the top to switch between event quality, errors and logs, performance, monitors, and custom app metrics. Then narrow the view with time range, environment, release, and attribute filters before opening the recent stream.

ControlBest use
Time windowStart with 24h for a balanced view, use 1h while debugging a deploy or incident, and use 7d to spot slow trends.
Environment and release filtersCompare production against staging, or isolate one deploy when validating whether a release changed error volume, throughput, or latency.
Custom attribute filtersFilter by stable top-level event context such as service, region, queue, tenant tier, job name, route, or feature flag. Keep values low-cardinality so the filter list stays useful.
Metric catalogAdd or remove collected series such as total events, errors, transactions, P95 duration, database query timing, and custom metric names.
Live refreshUse short refresh intervals during active debugging and longer intervals during passive monitoring to reduce unnecessary query load.
Recent streamOpen the newest matching events after narrowing the chart by time, environment, release, or custom attributes.

Good dashboard recipes

  • Release validation: filter to the new release, add total events, errors, transaction P95, and database query average, then compare the last hour with the previous day.
  • Instrumentation audit: use the metric catalog, recent stream, and performance page to confirm logs, custom metrics, transactions, spans, and check-ins are arriving from the expected service or environment.
  • Performance triage: add transaction P95, database query P95, request load spans, and error count so slowdowns and new failures share one timeline.
  • Operational monitoring: filter by job or queue attributes and add custom metric series such as queue depth, processed jobs, retry count, or worker latency.

Why some filters or charts may look empty

Charts can only filter and plot values that your app sends consistently. If environment or release menus are empty, the incoming events probably do not include those labels yet.

  • Use stable values such as service, region, queue, route, or tenant_tier.
  • Avoid raw IDs, emails, full URLs, and request bodies as chart dimensions.
  • Keep custom metric names stable and send a numeric value when you want a value chart instead of just a count.
  • Use faster live refresh only while actively watching a deploy or incident.

Recent stream

Use the stream after the chart has been narrowed.

  • FilterChoose the time, release, environment, and attribute slice first.
  • ConfirmCheck that the newest matching events have the labels you expect.
  • InspectOpen one row to move from trend-level signal into event detail.

Project lifecycle

Archive projects when you want history, delete only when you mean it.

Project lifecycle controls live in Settings because they change where the project appears in the UI. Archive is the reversible choice: the project leaves active dashboards and menus, but you can still find its history from archived views. Delete is the permanent choice and should only be used when the project and its history should disappear from the product.

ActionWhat changes in the UI
ArchiveThe project leaves active lists and dashboards, but remains available from archived project views.
RestoreThe project returns to active project views so the team can review it like any other app again.
DeleteThe project is removed instead of being kept for historical review.

Triage errors

Use Issues to decide what needs attention.

Issues shows grouped errors, not every repeated event. Use search when you know the message or fingerprint, the assignee menu when you are dividing work, and the status chips when you want open, introduced-today, resolved, ignored, archived, or all groups. The selected group opens on the right so you can act without leaving the list.

Prioritize

Find the errors that still need review

Use open, introduced-today, and assignee filters to focus on current work instead of already handled issues.

Act

Assign, mark fixed, ignore, archive, or reopen

Move an issue through the triage state that matches your team decision without losing its history.

Catch regressions

See when old problems come back

If a new occurrence arrives for a previously closed issue, Logister reopens it and preserves release context when your events include a release.

New to triage? Open the ? menu on Issues and choose Triage your first issue. It walks through one of the project's real open issues: read the issue, check what shipped, assign an owner, and close the loop. The choices you make change the issue for real, and you can leave at any step without changing anything you have not chosen.

Investigate faster

Open an issue and see the context around it.

The event detail pane is designed for the moment after you ask, "what happened here?" It combines payload context, stack or runtime details, occurrence history, and nearby logs that share the same trace, request, session, or user identifiers. Error details keep the main issue content in fixed-height panes so large payloads or long stack traces can scroll without pushing the rest of the workbench away.

What you needWhere Logister helps
Understand the failing request or jobSee the HTTP method and URL/path prominently when the integration sends request details, then read environment, release, request identifiers, user identifiers, and custom metadata.
Inspect the failure in the language you useUse runtime-aware views for Ruby, .NET, Python, JavaScript, and CFML so stack traces and log details match the shape of your app.
Compare repeats of the same problemOpen the occurrences tab to move between individual events in the same grouped issue.
Connect an error to nearby logsUse related logs to find log records in the correlation window instead of manually searching by request ID.

If related logs or release context are missing, the event may not include enough shared identifiers yet. Environment and release labels help you compare deploys. Trace, request, session, and user identifiers help Logister connect an error to nearby logs and repeated occurrences.

Connected projects · Logister 3.8+

Follow a mobile failure into its backend request.

Connect the app and backend from Settings > Connections with explicit environment mappings, enable related requests on the instance and both projects, and propagate request identifiers with a supported SDK. A connection grants no access; readers must already have access to both projects.

Start hereWhat to inspect
Error occurrenceRelated requests show captured HTTP outcomes, duration scope, app build/device details, issue ownership and each project's own release. Open the exact request or occurrence.
IssuesShow connected evidence adds badges for visible issues; the issue detail opens a report scoped to retained occurrences.
Overview, Explore › Events, or Performance (App health on mobile)Inspect connected impact by operation, release and app build. Filter the app and backend independently.
Release or deploymentInspect the selected build or compare observed related errors before and after a deployment.

Reports inspect up to 500 recent anchor records over at most seven days and show partial coverage. Peer counts include matching records only; installation and session counts stay within each mobile project. Observed matches and before/after counts do not prove cause or total traffic.

Issue JSON exports can optionally include connected evidence. Existing error emails resolve related records using the recipient's current access. Read connection setup and connected impact and its limits before using this workflow.

Understand performance

Turn transactions and metrics into a project performance view.

The project Overview gives you a quick read before you open deeper views. Use the timeline to see whether activity changed, the error group summary to see whether issues need review, and the request timing cards to decide whether latency deserves attention. The Performance tab holds the detail.

  • Transaction cards show volume, throughput, P50 latency, P95 latency, error rate, and Apdex for recent traffic.
  • Slow transaction rows highlight the slowest recent work and link to related errors when they share transaction context.
  • Database load appears when your app sends database timing metrics such as db.query.

Releases

Check what shipped, and what each release changed.

Releases > Deployments lists the deployments recorded for the project from CI, the CLI, or the HTTP API, with repository, environment, source, and search filters. Release health, below the list, shows each recent release with its total events, error events, introduced issues, and regressed issues when your events include a release name.

  • Android and iOS projects also have Releases, the builds observed in telemetry, and Artifacts, where you upload R8 mappings or dSYMs and see which builds they cover. Deploy records appears once a mobile project has recorded deployments.
  • If a release shows regressed issues, open Issues and filter to open groups; a regressed issue is one that was closed and has come back.

Watch scheduled work

Use check-ins for cron jobs, workers, and recurring tasks.

Scheduled work often fails quietly. Logister check-ins let each job report a slug, status, environment, expected interval, optional release, and duration. The Monitors tab, which appears once the project has a monitor, shows whether recent jobs are ok, in error, or missed based on the interval you set.

Check-in statusWhat it tells you
okThe job reported successfully within its expected cadence.
errorThe job reported a failed run.
missedThe job has not checked in within its expected interval plus grace time.

Review activity

Keep non-error telemetry visible too.

Explore › Events is the project activity feed. Use the type, period, environment, release, and search filters when you want to confirm that a signal arrived, find a specific log or metric, or open a non-error event with the same detail tools used for errors. Explore › Archive searches older telemetry and the archive runs that may hold it.

Email notifications

Send useful alerts without turning every occurrence into mail.

Notification settings are split by purpose so users do not have to understand every option at once. Start at Project > Settings > Notifications, choose the path that matches the reason for email, then tune that path only.

Work with teammates

Share project visibility without sharing every account credential.

Project owners can share access with existing Logister users by email. Shared users can open the project, review issues, assign and filter them, inspect Explore, Performance, and Monitors, and see Setup and the integration guidance. Settings > Team shows unresolved assignment counts beside members. Owners keep the sensitive controls: API key management, project sharing, editing the project in Settings > General, archive and restore, and deletion.

Admins can also use the admin area for account-level user cleanup and confirmation work when the instance is configured to grant them access.

Run it yourself

Use product settings for project-level decisions.

Most users only need the project UI: Setup for connecting an app, Issues for triage, Explore for review, and Settings for notifications, team access, and data cleanup. Instance-level setup lives in the operations docs so product pages can stay focused on what users see and choose inside Logister.

For project-level cleanup behavior, read the data retention guide. It explains what the Settings > Data choices mean before you change retention windows or archive settings.
